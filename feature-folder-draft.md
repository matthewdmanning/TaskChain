# Complete architecture: common, features and seams

Structured proposal for user verification · Baseline `a93d87a`, before PRs #44 and #45 · No source changes

All or nothing: this report defines one complete target architecture and maps the entire current Kotlin source inventory to it. It is not a menu of refactors, ranked candidates or a phased adoption plan. Feature availability is a runtime product choice within the target, not permission to implement only parts of the restructure.

## I. Conceptual ownership and seams

### 1. Design rules

| ID | Kind | Rule |
| --- | --- | --- |
| H01 | Hard | Core and shared are one common ownership area; display/navigation-only routine browsing belongs there. |
| H02 | Hard | Authoring is a feature over reusable definitions; execution snapshots and event history remain distinct shared record families. |
| H03 | Hard | No directed source dependency cycles, including via containers, receivers, launch targets or startup recovery. |
| H04 | Hard | Do not create competing authoritative stores for derived occurrence properties. |
| H05 | Scope | Define and verify the complete target and mapping before any moves. No behavior, storage migration or new CRUD operation is implied. |
| D01 | Design criterion | Weigh user value, lifecycle, interface depth, change locality, testability, flag semantics, blast radius and migration cost together. |
| D02 | Design criterion | Complete separation is not required. Useful one-way dependencies and shared capabilities are allowed; a cycle is not. |
| D03 | Design criterion | Hide substantial behavior behind small stable seams. A folder, pass-through service, extra ViewModel or interface is not inherently an improvement. |

### 2. Common / Core

Common has two dependency levels: reusable Core capabilities (C01–C07) and top-level executable wiring (C08). They are one ownership area. C08 remains root composition code; features depend on reusable Core, never on its executable assembly. These levels are not separate “core” and “shared” subsystems.

| ID | Common responsibility | Owns | Boundary / exclusion |
| C01 | Vocabulary and shared invariants | Routine definitions, run snapshots, completion/skip records, preferences, IDs, sound settings and validation used by multiple workflows. | Owns record meanings and cross-consumer validity; not feature workflows. |
| C02 | Stores and local durability | Definition, active-run, event and preference repository contracts; JSON/DataStore, atomic replacement, migration, asset loading. | One authoritative store per record family. No execution engine dependency. |
| C03 | Display, navigation and shared UI | Routine collection list/cards, route host, selection, generic controls, theme/provider implementations and semantic UI tokens. | Hosts injected feature content; imports no concrete feature screen, ViewModel or domain policy. |
| C04 | Shared recurrence and reminder planning | Recurrence calculation, reminder request/plan values and reusable save/completion/restore mapping. | Shared because multiple workflows and Android delivery use it. Does not own Today state or Android alarm lifecycle. |
| C05 | Shared output and platform contracts | Sound playback, task/timer audio and haptic output; reminder scheduling/delivery ports; launch-intent and lifecycle integration contracts where required. | Contracts and common output implementations only. Alarm ownership is F05; bubble policy is F07; run feedback eligibility is F04. |
| C06 | Time, configuration and availability | Clock, timezone/day-start configuration, packaged defaults and resolved feature availability. | Provides values; each behavioral owner interprets them. Availability policy does not erase saved data. |
| C07 | Startup and lifecycle host | Storage initialization/migration, startup ready/retry presentation and ordered execution of injected recovery/lifecycle hooks. | Runs a required execution-recovery hook without importing the execution engine. |
| C08 | Executable composition (common ownership) | Application/Activity entry wiring, construction of dependencies, route/capability registration and Android entry delegation. | Root source code may import Core and features. No reusable Core package or feature may import this root. This is wiring within common ownership, not another shared subsystem. |

### 6. Source dependency graph and cycle checks

Arrows mean imports/dependencies. Runtime callbacks can flow in the opposite direction without adding imports. Ownership groups must not be mistaken for dependency nodes: executable C08 can construct features, but reusable C01–C07 cannot import C08 or feature implementations.

> Diagram: Acyclic source dependency graph: common executable wiring depends on features and reusable common Core; features depend on reusable Core, with no back edge.
C08: Common executable assembly / Android entry wiringsupplies implementations, route content, launch factories and recovery hooksF01 Authoring · F02 Settings · F03 Scheduling · F04 ExecutionF05 Reminders · F06 Progress · F07 Quick returnC01–C07: Common reusable Core capabilitiesmodels, stores, UI/navigation, shared rules, output, time and startup host
| Proposed edge | Allowed / forbidden | Reason |
| C08 → feature implementations and C01–C07 | Allowed | Concrete construction is at the executable root. |
| Feature → needed Core contracts/services | Allowed | Shared stores/rules/output and generic UI are common. |
| Feature → another feature’s stable API | Allowed only one way, if justified and recorded | The selected target does not require these edges: shared ports/injected actions suffice. Do not mandate total separation if a simpler acyclic dependency wins. |
| C01–C07 → concrete feature or C08 | Forbidden | Would close a dependency loop because features/root already use Core. |
| Feature → AppContainer / TaskChainApplication / MainActivity | Forbidden in target | These root types construct or host features. Use required Core dependencies, provider contracts or injected launch actions. |
| C02 storage → F04 engine | Forbidden | RunRecovery must move to Execution and be invoked through a startup hook. |
| Core navigation → feature route registration callback at runtime | Allowed | The contract is defined by Core; construction/registration imports live only at C08. No hidden dynamic imports or event bus required. |

Proposed package topology
```
com/taskchain/
  core/
    model/ data/ browsing/ navigation/ designsystem/
    schedule/ platform/ time/ startup/
  features/
    authoring/ settings/ scheduling/ execution/
    reminders/ progress/ quickreturn/
  AppContainer.kt / TaskChainApplication.kt / MainActivity.kt
    # common executable assembly; no feature imports these roots

Feature internals preserve UI → ViewModel → domain and Android adapter boundaries.
This is source ownership in one :app module, not a requirement for new Gradle modules.
```
